# Чек-лист бизнес-приёмки ERD-схемы (Спринт 1)

**Назначение документа:** Чек-лист бизнес-валидации ERD-схемы хранилища данных перед утверждением архитектурного решения и началом написания SQL DDL скриптов. Документ обеспечивает соответствие проектируемой схемы требованиям бизнеса (каталогу требований FR/NFR) и бизнес-правилам домена (Domain Rules).

---

## 1. Гранулярность таблиц фактов (Fact Granularity)

- [ ] **Явная фиксация grain:** Для каждой таблицы фактов в документации ERD приведено однозначное текстовое определение гранулярности (в одно предложение: «одна строка представляет собой...»).
- [ ] **Отсутствие смешения уровней агрегации:** Ни одна таблица фактов не объединяет строки разной степени детализации (например, заголовок заказа и позиция заказа разнесены по соответствующим фактам).
- [ ] **Минимум 3 таблицы фактов разной гранулярности:**
  - [ ] **Факт продаж / позиций заказов (Transactional Fact):** гранулярность — одна строка на позицию заказа (`order_line_id` / заказ + SKU).
  - [ ] **Факт ежедневных остатков (Periodic Snapshot Fact):** гранулярность — одна строка на SKU / товар на конкретном складе за календарный день (`date_id` + `product_id` + `warehouse_id`).
  - [ ] **Факт событий / возвратов / логистики (Accumulating / Transactional Fact):** гранулярность — одна строка на событие возврата/рекламации либо веб-событие/сессию.

---

## 2. Полнота и структура измерений (Dimensions)

- [ ] **Минимум 5 аналитических измерений:**
  - [ ] **Измерение Даты / Времени (`dim_date`):** поддержка календаря, дня недели, месяца, квартала, года, признаков рабочих/выходных дней.
  - [ ] **Измерение Продукта (`dim_product`):** полная иерархия классификации: `Категория -> Подкатегория -> Продукт -> Вариант (цвет, память, размер) -> SKU / EAN` + Бренд.
  - [ ] **Измерение Клиента (`dim_customer`):** поддержка атрибутов профиля, сегмента, даты первой покупки.
  - [ ] **Измерение Канала продаж (`dim_channel`):** разделение собственного интернет-магазина и маркетплейсов.
  - [ ] **Измерение Склада и Перевозчика (`dim_warehouse`, `dim_carrier`):** склад отгрузки, служба доставки/курьерская компания.
- [ ] **Суррогатные ключи:** Все измерения используют синтетические целочисленные суррогатные ключи (`*_key` / `*_id`), отвязанные от естественных ключей источников.

---

## 3. Версионность и медленно меняющиеся измерения (SCD Type 2)

- [ ] **Поддержка SCD Type 2 для цен и себестоимости:** В измерении продукта (`dim_product`) или специализированном измерении цен предусмотрены поля версионирования:
  - `valid_from` (дата/время начала действия версии)
  - `valid_to` (дата/время окончания действия версии, либо `9999-12-31`)
  - `is_current` (флаг актуальной версии: `true`/`false`)
- [ ] **Связка с фактом продаж:** Факт продажи связывается с суррогатным ключом той версии товара, которая была актуальна на момент оформления заказа, что гарантирует точный расчет исторического COGS и валовой маржи.

---

## 4. Поддержка ключевых бизнес-сценариев (Domain Rules)

### 4.1. Заказ в нескольких посылках (Split-Shipment)
- [ ] Предусмотрена возможность разделения одного заказа на несколько посылок/отправок (например, отправка с разных складов или разными перевозчиками).
- [ ] Связь между позициями заказа и посылками (`shipment_id`) позволяет отслеживать статус доставки и сроки (Lead Time) по каждой посылке независимо.

### 4.2. Комплекты и наборы (Bundles)
- [ ] Модель поддерживает продажи наборов (Bundle SKU), состоящих из нескольких дочерних SKU.
- [ ] Предусмотрена таблица связи состава комплектов (`dim_bundle_component` / bridge-таблица) с указанием долей или коэффициентов списания для корректного списания складских остатков и декомпозиции COGS.

### 4.3. Жизненный цикл и статусы заказа
- [ ] Модель отражает статусы заказа: `оформлен -> оплачен -> отправлен -> доставлен / отменён`.
- [ ] Присутствует измерение статуса заказа (`dim_order_status`) или даты смены ключевых статусов для фильтрации валидной выручки (учет только оплаченных/доставленных заказов при расчете Net Sales).

### 4.4. Частичные возвраты и рекламации (RMA)
- [ ] Факт возвратов/рекламаций связывается с конкретной позицией исходного заказа (`order_line_id`).
- [ ] Поддерживается частичный возврат (возврат части количества штук из позиции заказа).
- [ ] Присутствует классификация причин и типов возврата: отказ от договора (возврат в срок) vs рекламация по качеству (брак).

### 4.5. Пропорциональное распределение скидки заказа
- [ ] В факте продаж предусмотрены поля:
  - `line_gross_amount` (стоимость позиции до скидки)
  - `line_item_discount_amount` (скидка на конкретную позицию)
  - `allocated_order_discount_amount` (доля общей скидки корзины/промокода заказа, распределенная пропорционально стоимости позиции)
  - `line_net_amount` (итоговая чистая сумма позиции для расчета Net Sales)

### 4.6. Разделение типов клиентов и требования GDPR/RODO
- [ ] Измерение клиента поддерживает разделение:
  - Гостевой заказ без регистрации (`is_guest = true`)
  - Зарегистрированный клиент B2C
  - Корпоративный клиент B2B
- [ ] Псевдонимизация ПДн: в витринах и слое аналитики отсутствуют открытые ФИО, email, телефон и точный домашний адрес (хешированы или маскированы); географический анализ ограничен уровнем города, региона и почтового индекса.
